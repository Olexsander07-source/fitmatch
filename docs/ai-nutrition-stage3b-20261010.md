## 1. Что реализовано

Существующий AI-помощник питания понимает создание дневного меню, вопрос «Что мне сегодня есть?», цели снижения/набора и вопрос о белке. Расчёт 3A и реальные сохранённые возраст, рост, вес, активность, цель, аллергены и пищевые предпочтения используются повторно. Нет выдуманного возраста, пола или массы тела. Недостающие сведения уточняются не более чем двумя вопросами за раз, затем тот же запрос меню продолжается после явного сообщения фактов.

Дневной рацион состоит из простых завтрака, обеда, ужина и перекусов. Указаны граммы или число яиц/бананов, сухая/сырая/готовая масса, примерные калории и БЖУ каждого приёма, дневная сумма, простой способ приготовления и общий список продуктов. Число приёмов 2–8 берётся из сохранённого предпочтения; по умолчанию четыре. Дополнительный перекус не может состоять только из кулинарного масла. При сохранённом одном приёме помощник предлагает выбрать практичное число 2–8, не назначая голодание.

Меню, точечные замены и подтверждение проходят контролируемый серверный сценарий без обращения к провайдеру. Обычные AI-вопросы, история, дневник питания, фотоанализ, подписки и тренировки сохраняются. Новых функций тренировок, аналитики или оплаты нет.

В существующих чате и разделе «Питание» доступны компактные карточки, кнопки замены отдельной порции, явное сохранение/отмена черновика и просмотр принятой версии. Новое предложение не скрывает факт существования текущего принятого рациона. На мобильном используются прежние цвета, панель и навигация FitGoIn, кнопки не меньше 44 px.

## 3. Как хранится рацион

Новые таблицы не вводятся. Принятый документ хранится в `public.fgi_ai_plans`: `kind='nutrition'`, `status='active'`, `schema_version=3`, `revision`, `supersedes_id`, снимок значимых данных профиля. Частичный уникальный индекс допускает только один активный рацион владельца. Предыдущая версия архивируется, её исходный документ сохраняется. Миграция сохраняет старые меню: последнее становится текущим, остальные — историей.

Предложение хранится отдельно в JSON собственного `fgi_ai_profiles.data.nutrition_plan_pending`: UUID, режим `request/proposal`, базовая версия, снимок предпочтений и проверенный документ. До подтверждения оно не становится строкой принятого плана. «Сохрани рацион», «Принимаю меню» или кнопка подтверждения принимают именно текущий черновик; случайное «Да» и обычный ответ AI этого не делают. Изменившиеся профиль, цель, число приёмов, базовая версия или выбранная карточка требуют обновить предложение, а не перезаписать чужую/устаревшую версию.

Прежняя `fgi_ai_complete` сохраняет сообщения, изменение памяти, черновик/принятую версию и retry-cache в одной транзакции. Повтор доставки с тем же request_id возвращает сохранённый результат; другой запрос с тем же nonce получает конфликт. Повторное подтверждение без черновика не создаёт дубль. Ошибка чтения или commit не возвращает «сохранено» и не заменяет текущий план.

Действующие RLS сохранены: браузер читает только собственные планы и профиль; не может INSERT/UPDATE принятый план или выполнить административную completion RPC. Backend сохраняет через прежнюю service-only RPC после настоящего Auth getUser, согласия, проверки доступа к модулю, владельца беседы и лимитов. Клиентский user_id не выбирает владельца.

## 4. Как выполняется замена

Каталог содержит 23 базовых продукта с приблизительной пищевой ценностью на 100 г, категорией, аллергенами, пределами/шагом порции и ориентиром стоимости/времени. Калории согласованы с порционными БЖУ по формуле 4/9/4. Это расчёт по общим продуктам, не точная этикетка конкретного бренда и не медицинская валидация. Основные пищевые группы сверены с [NHS Eatwell Guide](https://www.nhs.uk/live-well/eat-well/food-guidelines-and-food-labels/the-eatwell-guide/); справочный источник состава — [USDA FoodData Central](https://fdc.nal.usda.gov/). Записи каталога не выдаются за точную выгрузку индивидуальных FDC ID.

«Замени курицу», «Я не люблю овсянку», «У меня нет риса», «Я не ем рыбу» подбирают совместимый продукт и порцию, близкие по калориям/БЖУ. У явно указанной замены «на фасоль» может заметно снизиться белок и вырасти углеводы — это объясняется. Отображается численная разница за день. Другие ингредиенты и порции сохраняются буквально; изменение сначала становится черновиком.

Если продукт встречается в нескольких приёмах, обычная замена требует выбрать конкретную карточку. Явный устойчивый отказ от продукта заменяет все его вхождения и обновляет пищевую память 3A; общий отказ от рыбы включает лосось. «У меня нет риса» не создаёт постоянный запрет. Положительное «Люблю рыбу» не исключает рыбу. «Сделай дешевле/быстрее» меняет только подходящие позиции с близкими макросами; точные цены не выдумываются. Суточное число яиц при таких заменах не увеличивается выше трёх.

## 5. Какие проверки прошли

- `npm run check`: 151/151, без отказов. `npm run deploy:dry`: после установки закреплённых lockfile зависимостей завершился кодом 0, Wrangler сообщил `--dry-run: exiting now`, подготовлены 33 файла сборки. Это Linux-проверки кандидата, не подмена обязательных Windows-команд.
- Реальная PostgreSQL-транзакция с кандидатной функцией и индексом: черновик отдельно от принятого плана, запрет неподтверждённой/другой версии, принятие, смена версии/архив, повтор completion без дубля, устаревший профиль/базовый план и отсутствующий режим без частичной записи, чтение актуальной версии владельцем, запрет чтения/изменения другим authenticated владельцем, запрет browser RPC и INSERT/UPDATE plans. Всё откатилось. Свежая проверка: ноль двух временных пользователей/планов, индекс кандидата отсутствует. SQL использует компактные порционные storage fixtures; полная проверка состава выполняется серверными тестами.
- Браузер: 40 проверок настоящих frontend и handler на 360/390/768/1440 px. Создание → замена одной порции → подтверждение → сохранение → reload с точным новым продуктом/граммами → повторный вход. Проверены сохранённые предпочтения, отмена нового предложения, очистка UI при смене аккаунта, ошибка Supabase commit/load, отсутствие горизонтального переполнения и размер кнопок. Нет ошибок JavaScript; провайдер не вызывался. Auth/REST в этом прогоне изолированы в памяти: это не production Auth acceptance и не доказательство RLS, которое проверено отдельно настоящим SQL.
- Прежние проверки API/provider/nonce/consent/module isolation, training, voice, billing и безопасного hosting входят в 151 тестов и проходят.

Evidence: `qa/ai-stage3b/ui-acceptance.json`, `nutrition-390.png`, `nutrition-1440.png`, `sql-acceptance.json`.

## Продолжение

Не создавать проект заново и не повторять публикацию 3A. После появления компьютера online использовать свежий отдельный чистый clone кандидата, затем `npm.cmd run check` и `npm.cmd run deploy:dry`; прочитать результаты до merge. Не использовать старый checkout без git status: наш прошлый вызов CLI migration new мог оставить там пустой файл. После зелёных проверок и CI принять PR в main, синхронизировать чистый checkout с origin/main, применить проверенную миграцию один раз, опубликовать полный backend с прежней custom Auth getUser, затем только `npm.cmd run deploy` через `scripts/safe-deploy.mjs` в `fitgoin-production`. Legacy Worker `fitgoin` не использовать. Секреты не выводить. Старую остановленную задачу ожидания компьютера не включать повторно.
