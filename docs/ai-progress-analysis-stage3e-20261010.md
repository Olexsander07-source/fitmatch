## 1. Реализованная логика

В «Мой прогресс» добавлен разбор последних 28 дней; через чат можно указать 7–56 дней. Расчёты выполняются кодом и PostgreSQL до обращения к модели. Обычный чат предупреждён, что его небольшая выборка недавней истории не позволяет вычислять полные итоги периода.

**Вес.** Используются реальные `recorded_on` и `weight_kg`; при нескольких измерениях за день для анализа берётся последнее, сами записи не удаляются. Указываются фактические первая/последняя даты, число дней и разница. Например, в тесте 85,6 → 83,5 кг за 27 дней даёт −2,1 кг; этот результат не выдаётся за четыре полные недели. Без двух разных дат динамика неизвестна. Изменение веса профиля после измерения само по себе не блокирует анализ прежней программы; изменения цели, оборудования, графика и других спортивных условий требуют пересмотра.

Для трёх и более дат на протяжении минимум 14 дней диапазон до 0,5 кг вызывает предложение проверить условия взвешивания и фактическое питание. Набор более 1% начального веса за неделю в таком интервале вызывает предложение сверить измерения и фактическую калорийность. Эти пороги — ограниченные продуктовые эвристики, не диагноз и не основание автоматически менять калории. Без свежего измерения за последние семь дней такие советы не выдаются. Явная цель веса из профиля может дать предложение обсудить её обновление; цель автоматически не записывается.

**Тренировки.** Число `completed` с известным `completed_at` рассчитывается по всем строкам владельца за интервал. Остановленные и активные занятия исключены. Сложность оценивается по известным оценкам последних 12 завершённых записей, отсутствующая оценка не становится нулём. Ответ явно называет размер этой выборки.

**Плановый календарь.** Учитываются только полные прошедшие дни с достоверным календарём schema 2, фиксированными weekday и тем же часовым поясом. RPC восстанавливает действовавшую на день версию по цепочке `supersedes_id`; смена версии внутри дня делает его неизвестным. Сегодня, дни до создания программы, последовательные планы без календаря и неподтверждённые часовые пояса исключаются. Формулировка: «X из Y плановых занятий имеют связанную запись о завершении». Отсутствие строки не доказывает реальный пропуск, несвязанные занятия также не считаются пропуском.

**Упражнения.** Сравниваются две последние реальные записи до десяти упражнений. Прямое изменение рабочего веса показывается только при одинаковом числе подходов и одинаковых известных повторениях, с известным одинаковым весом внутри занятия. Различающиеся условия обозначаются как несопоставимые. Плановые веса и повторения не подставляются; максимальная сила не оценивается.

**Питание и восстановление.** Отдельно показываются реальные строки дневника, число записанных дней, суммы калорий/БЖУ в этих строках и среднее по записанным дням. Полнота дня не подтверждается. Наличие сохранённого меню показывается отдельно: меню — план, не доказательство соблюдения. При тяжёлых занятиях предлагается проверить сон, восстановление, фактическое питание и нагрузку. Рацион не переписывается.

**Безопасность.** Текущая боль в груди, потеря сознания, резкая одышка и серьёзная травма прерывают обычные советы: остановиться и обратиться за срочной медицинской помощью. Диагнозы и неизвестный местный номер не придумываются. Отрицание боли и гипотетические вопросы не создают ложную травму. Реальные признаки риска блокируют прогрессию; обычные сообщения не получают медицинского предупреждения. При успешном сохранении используется существующая остановка фактической сессии и `needs_professional`. При ошибке базы или лимите срочный ответ всё равно виден, с честным сообщением, что сохранение остановки/истории не подтверждено.

## 2. Данные и хранение

**Новых таблиц и полей нет.** Используются:

| Данные | Источник |
| --- | --- |
| Датированные измерения | `fgi_ai_progress` |
| Выполненные занятия, сложность, комментарии, подходы | `fgi_ai_workouts` из 3C |
| Версии программы и плановое меню | `fgi_ai_plans` |
| Фактические продукты | `fgi_ai_food` |
| Цель, ограничения и приватный черновик | `fgi_ai_profiles.data` |
| Диалог, сообщения и повтор доставки | Существующие conversations/messages/requests |

Миграция `20261010132150_ai_progress_analysis.sql`, созданная штатным Supabase CLI, добавляет два service-only RPC:

- `fgi_ai_progress_analysis`: согласованный снимок всех источников в одном SQL statement; owner-фильтры и модульные права.
- `fgi_ai_progress_complete`: дополнительные проверки адаптации под той же блокировкой профиля, затем вызов существующего `fgi_ai_complete` из 2C.

Оба — `SECURITY INVOKER`, пустой `search_path`, EXECUTE только для `service_role`; browser/anon не могут передать чужой ID этим RPC. Backend получает владельца через проверенный Supabase Auth; клиентский `user_id` игнорируется. Обычный доступ к журналам сохраняет owner-only RLS.

Черновик сохраняется в действующем `program_edit_pending`: ID предложения, владелец через строку профиля, программа, диалог, время, интервал, снимок спортивных условий, изменения before/after и ID/revision реальных тренировок-оснований. Числовые итоги разбора сохраняются в ответе существующего диалога, без отдельной аналитической таблицы.

## 3. Согласование и новая версия

1. Три последние завершённые тренировки текущей программы со сложностью 8–10/10 дают предложение убрать один подход у одного упражнения с несколькими подходами в каждом занятии. Минимум один подход сохраняется; отдых, разминка, завершение и остальные упражнения остаются.
2. Два последних выполнения одной тренировки текущей программы со сложностью 1–3/10 и реально записанными целевыми подходами/повторениями допускают предложение добавить одно повторение в одном упражнении. Рабочий вес не увеличивается. Время пересчитывается и проходит прежнюю валидацию.
3. AI объясняет причины и точные before/after. Запрос анализа сохраняет только черновик; активная программа остаётся прежней.
4. «Не меняй программу» удаляет только предложение. Для снижения объёма требуется «Сохрани адаптацию» или кнопка. Для прогрессии дополнительно требуется явное подтверждение «техника уверенная, боли нет»; checkbox в UI отражает эти условия.
5. При согласии повторно читаются история и профиль, проверяются та же программа/диалог/черновик, срок 24 часа и те же реальные основания. Изменившиеся данные, активная сессия, старый cursor без реальной сессии, новые признаки боли или другое предложение отклоняются.
6. SQL под блокировкой профиля ещё раз сверяет последние ID/revision тренировок, текущую активную программу и риск. Дальше **существующая 2C транзакция** архивирует прежнюю строку, создаёт новую с `revision + 1` и `supersedes_id`, сохраняет диалог и ответ. Исторический документ и выполненные результаты не изменяются.
7. Тот же delivery nonce возвращает сохранённый результат без второй версии. Потерянный ответ восстанавливается загрузкой истории. Внутренние инструкции RPC не возвращаются в browser или retry cache.
8. Незавершённая замена упражнения из 2C не перезаписывается новым предложением; подтверждение завершения тренировки из 3C имеет приоритет над общим «Да».

При недостатке связанных календарных записей предлагается обсудить более реалистичные дни/частоту, без утверждения, что пользователь пропускал. Частота и цели пока обсуждаются через существующее изменение программы; 3E самостоятельно не перестраивает весь календарь.

## 6. Ограничения и оставшаяся публикация

- Управляемые основные команды анализа русские; обычный чат на других языках сохраняется, но не подменяет полный SQL разбор.
- Интервал 7–56 дней. Сложность — выборка последних 12 записей; упражнений — до десяти сравнимых пар. Общий счёт выполненных тренировок полный.
- Сохранённый weekday-календарь, его версии и часовой пояс должны быть известны. Прошедший день смены версии и сегодня исключены; неизвестный график не экстраполируется.
- Нельзя доказать полноту дневника или соблюдение меню. Изменения калорий и диагнозы не автоматизированы.
- Сохраняемые предложения 3E ограничены снижением подходов и одним дополнительным повторением. Сложные rep ranges, автоматическое увеличение рабочего веса, полная смена календаря и цели не добавлены. Если все упражнения имеют один подход, автоматического уменьшения подходов нет.
- Фактический вес после нового измерения не считается сменой спортивных условий; новое ограничение/цель/оборудование блокируют адаптацию. BMI/возраст и прежние safety ограничения продолжают действовать.
- При сбое сохранения срочный ответ остаётся видимым, однако отметка остановки/профиля может не сохраниться; интерфейс явно говорит об этом.
- Физический iPhone/Safari, реальные production Auth/REST/Edge сценарии 3B–3E и Windows check/dry остаются непроверенными.
- Все 3B–3E остаются кандидатами. Production не менялся; компьютер для разрешённого safe-deploy Offline.
