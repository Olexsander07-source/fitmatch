## 1. Что реализовано

- Использованы действующие программы и **существующая** `public.fgi_ai_workouts`. Простой cursor этапа 2C и прежний дневник подходов теперь открывают одну сессию, показывают её реальные упражнения и результаты.
- «Сегодняшняя тренировка», «Моя программа», переход к следующему упражнению и запись подхода доступны через существующие разделы AI. Кнопка «Завершить тренировку» открывает подтверждение с необязательными длительностью, сложностью и комментарием.
- «Я закончил тренировку» создаёт сохраняемое ожидание подтверждения. Завершение фиксируется только после «Подтверждаю завершение тренировки» или подтверждения в форме. Пример с явно указанными значениями: «Я закончил тренировку за 45 минут, сложность 8/10; комментарий: хорошо».
- «Жим лёжа 80 кг, 4 подхода по 8» привязывается к фактическому упражнению открытой тренировки. В форме можно записывать отдельные подходы с повторениями, необязательным весом, сложностью подхода и комментарием.
- Неизвестные длительность, вес и сложность остаются `null`. Прежняя автоматическая подстановка сложности 7 устранена также в голосовом вводе. Плановые подходы и длительность не становятся выполненными автоматически.
- При нескольких открытых тренировках требуется выбор; при неоднозначном названии упражнения — полное название или выбор в карточке. До уточнения результат не записывается.
- Записанные подходы, состояние и завершённый результат загружаются после обновления страницы. При смене аккаунта прежнее состояние интерфейса очищается.
- Повторный старт открытой тренировки продолжает ту же сессию. Повторное завершение сохраняет первоначальную строку и timestamp. Повтор одинакового группового отчёта не добавляет ещё четыре подхода; отдельные реальные подходы в форме остаются добавляемыми.
- Остановка из-за боли сохраняет записанные подходы со статусом `stopped`, без отметки выполнения. Прежние проверки необходимости пересмотра программы сохранены.

Питание, сохранённый документ программы и существующие разделы аналитики не перерабатывались. Следующие этапы не начаты.

## 3. Таблицы, поля и сохранение

**Новых таблиц нет.** Миграция создана настоящей командой Supabase CLI `migration new ai_workout_completion_log`.

В `fgi_ai_workouts` добавляется целочисленная `revision` для защиты от устаревшего сохранения. Прежние `user_id`, `plan_id`, `started_at`, `completed_at` остаются источником владельца, связи с программой и времени. `data.workout` содержит snapshot выбранной тренировки и её ID; `data.sets` — только заявленные пользователем выполненные подходы. Новые `data.reports` предотвращают повтор группового отчёта. В `data` сохраняются `status`, необязательные `duration_minutes`, `difficulty`, `comment` и прежнее состояние упражнения/отдыха.

В личном `fgi_ai_profiles.data.current_workout` используется `session_id` существующей строки. `workout_log_pending` хранит только ожидание подтверждения: ID сессии, её ревизию и введённые значения. Этот черновик не означает выполнения.

Backend получает владельца через проверку токена в Supabase Auth; клиентский `user_id` не используется. Изменения сессии, сообщения пользователя/AI и результат delivery nonce выполняются одной транзакцией `fgi_ai_complete`. Внутренняя `fgi_private.ai_workout_change` повторно проверяет владельца, snapshot упражнения и ревизию. Подтверждение возвращается после успешной записи. При ошибке откатываются и результат, и сообщение «сохранено».

Завершённая строка защищена от случайной перезаписи. Существующее удаление личных данных и `ON DELETE SET NULL` для программы сохранены. Старый cursor 2C переносится в ту же таблицу при первом реальном результате с исходным известным временем открытия. Старые упражнения без ID получают устойчивую ссылку по индексу snapshot; сам snapshot не переписывается.

## 4. Безопасность и ошибки

Действующая owner-only RLS `fgi_ai_workouts` сохранена с проверкой `auth.uid()` в USING/WITH CHECK. Таблица остаётся с включённой RLS. Внутренний helper и `fgi_ai_complete` недоступны `anon`/`authenticated`, вызываются только сервером; функции используют `SECURITY INVOKER`, пустой `search_path` и явные owner-фильтры. Foreign session, exercise и stale revision отклоняются.

Ошибка Supabase/API видна пользователю. Неоднозначная доставка сохраняет прежний nonce до проверки истории, чтобы повтор не создавал результат заново. В retry cache не копируется внутренний массив изменений. Комментарии экранируются при показе. Секреты не включены в код, отчёт и доказательства.

## 6. Ограничения и оставшаяся публикация

- Поддерживается базовый числовой отчёт вида «название, 4 подхода по 8, 80 кг» / `4×8` и форма отдельных подходов. Свободные описания сложных схем, timed sets и автоматическое редактирование завершённой истории не добавлены.
- Для записи через чат/форму сохраняются действующие права на модуль и лимиты AI-запросов. Команды сохранения не вызывают модель и не выдумывают измерения.
- Одинаковый групповой отчёт считается повтором. Для дополнительного реально выполненного такого же подхода используется форма отдельного подхода.
- Публикация требует доступного DESKTOP-EJAAHVB и чистого Windows checkout. Затем обязательны `npm.cmd run check` и `npm.cmd run deploy:dry`, включение проверенного 3B и этого 3C в `main`, последовательное применение миграций 3B/3C, полная Edge Function с девятью исходными файлами (index + восемь импортов), затем **только** `npm.cmd run deploy` через `scripts/safe-deploy.mjs` в `fitgoin-production`.
- После публикации необходимы проверка release SHA/AI assets и авторизованный acceptance на реальном сайте с двумя отдельными QA-аккаунтами. Такой production прогон 3C пока не проводился. Legacy Worker `fitgoin` не используется.

Справочные правила проверены по официальным [Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security) и актуальному [changelog](https://supabase.com/changelog.md). Изменения вне этапа 3C не добавлялись.
