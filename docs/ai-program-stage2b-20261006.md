## 2. Структура программы

Использована существующая `public.fgi_ai_plans`, `kind='training'`, со связью `user_id` с авторизованным владельцем. JSONB `document` имеет `schema_version=2`, название, краткое описание, правила постепенного изменения нагрузки и `schedule`.

Каждая тренировка содержит стабильный внутри версии UUID, номер, явный день недели либо `day=-1` для последовательности, название, цель, продолжительность, разминку, завершение и упражнения. У упражнения есть UUID, название, подходы, повторения/время, отдых, продолжительность с отдыхом, краткая техника, нужное оборудование, альтернатива и оборудование альтернативы. Это отдельные поля и массивы, а не только большой ответ AI.

Такой документ позволяет в дальнейшем адресовать конкретное упражнение и сохранить исправленную версию через серверную проверку. Редактор отдельных упражнений в 2B не добавлялся.

## 5. Как формируется персональная программа

Запросы «Составь мне программу», «Создай программу тренировок» и «Что мне лучше тренировать?» распознаются в существующем тренировочном чате. Сервер получает владельца из проверенного Auth JWT и читает его действительную спортивную память. Значения нормализации формы не подставляются как известные факты.

Обязательный минимум: цель, уровень, частота, длительность, место, оборудование, добровольно сообщённые ограничения/травмы. Явное «ограничений нет» отличается от неизвестного значения. Если минимум неполон, приложение спрашивает максимум два недостающих поля и сохраняет `program_pending` в существующей памяти; уже известные поля не спрашивает. Имя, возраст, спорт и дни недели не являются дополнительными обязательными вопросами. Известный возраст/опыт и дополнительные спортивные факты используются, когда они действительно сохранены.

После последнего уточнения проверенный memory patch и новая программа сохраняются вместе. Модель получает actual facts, а не общий шаблон: цель/целевой результат, уровень/подробный опыт, число тренировок, время, место, инвентарь/вес инвентаря и ограничения. Она возвращает строгий JSON; сервер проверяет число тренировок, последовательность, строки, подходы, доступное оборудование и работающую альтернативу без исходного инвентаря.

Время считается приложением: сохраняются предложенные подходы, повторения и отдых, исправляется лишь заниженная оценка минут. Для timed sets учитывается назначенное время; для повторений используется нижняя оценка 20 секунд на подход. В каждой тренировке зарезервированы пять минут разминки и три завершения. Программа сверх бюджета отклоняется; AI получает конкретную причину/числовые данные для одной попытки исправления. Если исправление не прошло, программа не сохраняется. Это приблизительная оценка, не live-измерение занятия.

Существующий защитный режим для несовершеннолетних, сообщённых медицинских ограничений и опасного дефицита массы сохранён: такая персональная нагрузка требует специалиста. Этап не обещает автоматическую лечебную программу при травме.

`program_pending` продолжает intake только в модуле тренировок. Переключение другого существующего AI-модуля не создаёт там тренировочную программу и не подменяет его разговор уточнениями 2B.

## 6. Как сохраняется программа

`fgi_ai_complete` проверяет актуальный профиль, принадлежность диалога, доступ и pending request, блокирует профиль и прежнюю активную версию. Проверяется ожидаемый ID прежней программы. Затем в **одной транзакции** записываются разрешённые факты/состояние intake, два сообщения, архивирование прежней версии, новая активная версия и cache завершённого запроса.

Если новая вставка или любая проверка не проходит, вся транзакция откатывается: предыдущая программа не исчезает, новая не активируется, сообщение «сохранено» не появляется. Ответ с `program_saved=true` возвращается только после успешного RPC. Повтор прежнего `request_id` не создаёт другую программу. Прямые клиентские INSERT/UPDATE и вызов completion RPC запрещены.

## 7. Загрузка после перезагрузки и повторного входа

При восстановлении сессии интерфейс заново читает собственный `fgi_ai_plans` с `kind='training' AND status='active'`. Session storage нужен только для черновика/доставки, не служит хранилищем программы.

«Покажи мою программу» и «Какая у меня программа?» получают актуальную запись БД. AI-provider для этих запросов не вызывается и новая программа не генерируется. В карточках сохраняются прежние ID и версия.

## 8. Активная версия и согласованность с памятью

Одна активная программа обеспечивается уникальным индексом. При успешной замене увеличивается `revision`, сохраняется `supersedes_id`, предыдущая версия остаётся архивной. Параллельная замена со старым ожидаемым ID отклоняется.

Snapshot сравнивается с текущими спортивными фактами независимо от порядка ключей JSONB. Если профиль изменился, интерфейс и сохранённый ответ сообщают, что программу надо пересмотреть; старый документ не объявляется автоматически адаптированным.

Дни недели не выдумываются. Когда они явно сохранены и их количество совпадает с частотой, программа получает `schedule.mode='weekdays'`; иначе это `sequence`. «Сегодня/завтра» используют действительный часовой пояс клиента либо сохранённый пояс и календарную дату. Для последовательности или отсутствующего часового пояса приложение объясняет неопределённость. День отдыха тоже читается из расписания, не превращается в случайную тренировку.

Помимо сравнения snapshot, новый флаг `needs_professional` требует пересмотра сохранённой программы, даже если остальные спортивные значения прежние. Это предупреждение отображается в сохранённом ответе и мобильных карточках; рабочая предыдущая версия не удаляется.

## 9. RLS и границы клиента

RLS существующей `fgi_ai_plans` оставлена включённой. SELECT/DELETE ограничены `auth.uid()=user_id`. Authenticated не имеет INSERT/UPDATE программы или EXECUTE `fgi_ai_complete`; сервер использует собственную проверку JWT и validated completion, игнорируя подставленный владельцем запроса `user_id`. Service-role key во frontend отсутствует.

Два настоящих Auth JWT подтвердили отсутствие чтения, изменения и удаления чужой программы. Отдельно проверен запрет поддельного вызова completion RPC. Проверки SQL также контролировали чтение владельцем своих архивных версий, откат неудачной вставки после архивирования и отклонение устаревшей замены.

## 12. Оставшиеся проблемы и публикация

1. Production frontend 1/2A/2B требует разрешённого безопасного deploy. DESKTOP-EJAAHVB offline; `npm.cmd run deploy` в этом этапе не выполнялся. Версия сайта и загрузка нового модуля на fitgoin.com пока не подтверждены.
2. Реальный iPhone/Safari не проверен; эмуляция Chromium не закрывает эту приёмку.
3. Строгая структура и арифметика не гарантируют индивидуальную пригодность каждого упражнения. При появлении production следует отдельно оценить понятность/сложность нескольких программ; медицинские ограничения остаются за существующим protective gate.
4. Возможны отказы или задержки внешнего AI/сети; подтверждение сохранения и прежняя версия защищены. Нет обещания успешной генерации любого произвольного запроса.

Security Advisor не выявил нового предупреждения безопасности. Прежние server-only RLS INFO сохранены. Существующий Auth warning о [защите от скомпрометированных паролей](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection) остаётся; настройки Auth в 2B не менялись.

Для публикации прочитать `AGENTS.md` и актуальный `fitgoin-ai-resume.md`; взять отдельный чистый checkout проверенной актуальной `main`, сохранив чужую работу. Выполнить `npm.cmd run check`, `npm.cmd run deploy:dry`, затем **только `npm.cmd run deploy` через `scripts/safe-deploy.mjs` в `fitgoin-production`**. Не использовать legacy Worker `fitgoin`. После deploy сверить release SHA/assets, загрузку `fitgoin-ai-program.mjs` и авторизованный мобильный сценарий на https://fitgoin.com. Не менять функции и не начинать 2C в процессе публикации.
